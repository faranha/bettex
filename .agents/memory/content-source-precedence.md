---
name: BETTEX content source precedence
description: How to reconcile legacy whitepaper wording with creator-approved product rules.
---

When revising BETTEX's presentation, use the creator's latest explicit instructions and the approved product rules in replit.md as the source of truth. Do not restore a rule merely because it appears in the Git baseline of the whitepaper.

If the creator explicitly says the saved rules are outdated, their correction takes precedence over replit.md too. Use history to locate the earlier work, but distinguish the specifically confirmed correction from other historical prices, calendars or integrations that have not been reconfirmed.

**Why:** Both whitepaper content and saved project instructions have retained incompatible economic models. Preserving numbers solely because they match the current code or instructions can perpetuate a regression; restoring an entire old file can also undo later wallet and access corrections.

**How to apply:** Audit substantive figures and rules across the landing, app presentation and whitepaper together. Distinguish alignment with an already approved rule from introducing a new economic rule; do not invent allocations, vesting dates or guarantees.

After merging isolated work, compare the result with the most recent approved presentation, not only with the isolated branch's starting point.

**Why:** A merge passed compilation and content audits while undoing recently approved copy limits and mobile styling. Technical validation alone does not establish that editorial and visual approvals were preserved.

**How to apply:** Reconcile conflicting changes at the affected fields or branches, preserving newer approved content elsewhere. Do not restore whole files from an older version just to repair a localized regression.

Do not treat initial-financing allocation as permanently unconstrained. Apply the latest funding-source-specific destination rules in replit.md, rather than restoring an old split or an old blanket free-allocation statement.

**Why:** The creator revised financing use more than once. Both the old mandatory split and a later blanket free-allocation statement can contradict newly approved restrictions for a specific financing source.

**How to apply:** Distinguish angel contributions, public primary token-sale proceeds, treasury profit distribution and the founder’s own token earnings. Changing financing-use restrictions does not automatically change token percentages, vesting or the profit split. Reconcile all affected Pitch sections without overwriting unrelated approved content.
